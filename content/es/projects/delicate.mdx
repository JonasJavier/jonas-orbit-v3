## 1. Contexto

Delicaté es un producto web para un negocio real de jabones artesanales. El
objetivo era presentar la marca y el catálogo con una experiencia propia, y abrir
un canal de pedidos que el negocio pudiera atender con su operación actual.

## 2. Problema

Una tienda con checkout, pagos e inventario promete una operación que no siempre
existe detrás. En este caso el negocio necesitaba mostrar productos, ayudar al
cliente a elegir y recibir un pedido bien formado, pero la confirmación y el cierre
seguirían ocurriendo por WhatsApp.

## 3. Objetivo

Crear una experiencia responsive que conectara descubrimiento de marca, exploración
del catálogo, selección de productos y envío del pedido, con un catálogo que el
negocio pudiera administrar sin tocar código.

## 4. Mi función

Me encargué del levantamiento de necesidades, arquitectura de información, UX/UI,
desarrollo de frontend y backend, integración del flujo de pedido y preparación de
la entrega técnica.

## 5. Usuarios

El cliente final explora productos, filtra por necesidades, revisa detalles y arma
su carrito. El negocio administra el catálogo desde Django y recibe en WhatsApp un
resumen legible con productos y cantidades.

## 6. Restricciones

El alcance no incluye pagos en línea, seguimiento logístico ni promesas de stock en
tiempo real. El flujo debía funcionar bien en móvil, conservar el carrito entre
visitas y permitir que el catálogo cambiara sin recompilar el frontend.

## 7. Proceso

Partí del recorrido comercial real: descubrir la marca, encontrar un producto,
comparar beneficios, construir el pedido y abrir la conversación. Separé el
catálogo administrable de la presentación pública y probé el flujo completo con
datos de demostración.

## 8. Decisiones importantes

- API pública de solo lectura para el catálogo y administración protegida en Django.
- Carrito persistido en `localStorage` para evitar perder la selección.
- Pedido estructurado por WhatsApp como cierre real del proceso.
- Filtros por categoría y beneficio para reducir la exploración manual.

## 9. Arquitectura y stack

El backend usa Django 5.2 y Django REST Framework 3.17; el frontend usa React 19 y
Vite 8. PostgreSQL es la base recomendada para producción. La API expone el
catálogo y React mantiene el estado de exploración y carrito en el cliente.

## 10. Desafíos

El principal desafío fue construir una experiencia de compra convincente sin
inventar una infraestructura de pagos o logística. También hubo que mantener
consistencia entre el catálogo administrado, los filtros, el detalle y un carrito
que sobrevive a la recarga.

## 11. Soluciones implementadas

El catálogo se consulta desde la API y se presenta con estados claros. El carrito
normaliza cantidades, calcula el resumen y genera un mensaje de WhatsApp con el
pedido. La aplicación contempla estados vacíos y de error, y mantiene separadas las
responsabilidades de contenido, selección y cierre.

## 12. Diseño y UX

La dirección visual usa una paleta cálida, fotografía de producto y composición
editorial para comunicar artesanía. En interacción, los diálogos controlan el foco,
existe soporte para `prefers-reduced-motion` y el flujo conserva acciones claras en
escritorio y móvil.

## 13. Capturas y demo

La selección muestra portada, catálogo, detalle, carrito y variantes móviles. Los
diez productos visibles durante la captura son datos de demostración preparados
para validar la interfaz, no una afirmación sobre el inventario comercial actual.

## 14. Resultados verificables

La API y el frontend funcionan de extremo a extremo; las 12 pruebas automatizadas
pasan; Django no reporta problemas de sistema ni migraciones pendientes; y el
frontend supera lint y build de producción. No se atribuyen ventas ni conversiones
porque todavía no existe evidencia de negocio publicada.

## 15. Aprendizajes

Un buen producto no necesita fingir más infraestructura de la que el negocio puede
operar. Ajustar el cierre a WhatsApp convirtió una limitación real en un flujo
coherente, medible y fácil de adoptar.

## 16. Estado actual

El producto está técnicamente listo para desplegar. Antes de la salida comercial
faltan las validaciones operativas indicadas por el negocio —contenido final,
contacto, variables y revisión del proceso de atención—, por eso no se etiqueta aún
como “en producción”.
